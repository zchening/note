### 更新内容

- 原生桥提到剪贴板之前
- 壳内不再走假成功的剪贴板
- 复制后读回验证再报成功
- 验证为空不许谎报已复制

用户报障：App 里「导出为图片并复制」点了之后，微信粘不出、小米自带笔记
也粘不出 —— 等于**压根没进系统剪贴板**。

真因在 Chromium 源码里，不在我们代码里：
`ui/android/java/src/org/chromium/ui/base/ClipboardImpl.java`

```java
public void setImage(final byte[] imageData, final String extension) {
    if (mImageFileProvider == null) {
        // ...we can just drop it on the floor.
        return;
    }
```

`ImageFileProvider` 只有 Chrome 自己注入（ChromeImageFileProvider），
WebView 宿主（Capacitor 壳）**从不注入** ⇒ 壳内
`navigator.clipboard.write(ClipboardItem{'image/png'})` 被**静默丢弃**；
而 C++ 侧 `Java_Clipboard_setImage` 是 void、不检查返回值 ⇒
**promise 照常 resolve**。于是交付阶梯在剪贴板档就 return、弹「已复制」，
真正能写系统剪贴板的原生桥（ImgClip）**永远轮不到**。

修复三件：

1. 壳内把**原生桥提到剪贴板之前**（ImgClip → `ClipboardManager` 真写）；
2. 壳内**不再走 WebView 剪贴板那一档** —— 它在壳里只会假成功，
   桥一旦失败就该老实去分享/预览，而不是给用户一句假的「已复制」；
3. 桥写完**读回验证**（新增 `ImgClip.hasImage`，三态 `ok/hasImage/mime`）：
   `ok:false` = 读不回来 ⇒ 无法证伪，信任写入；`hasImage:false` = 剪贴板里确实没图
   ⇒ 不许回报成功，继续走分享/预览。旧 APK 没有 `hasImage` 时按「无法证伪」处理。

（AOSP `ClipboardService.addActiveOwnerLocked` 会在接收方 `getPrimaryClip`
时授予 content URI 读权限 —— 所以桥那条路在系统层面是通的，之前只是没走到。）
