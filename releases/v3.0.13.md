v3.0.12 真机日志复盘：贴出的 400 条 ring 末尾段里**没有丢字**——组字串
逐帧全长替换、真源 1:1 跟随（upd len 22→38 与 data 长度逐帧相等）、同步
合并干净、推送成功；且每帧 `in:i comp=1` 都没有 `sel:orphaned`，说明整个
窗口内 `ed.isComposing()===true`（组字态成立）。但这段无法钉死 ① 是否
触发过：ring 会滚动，组字起点早被挤掉；`in:bi` 又不记 `comp=` 位。取证
链上有盲区，就不许下"修好了/没修好"的结论。

本版只做取证加固、**零行为变更**：

**全程计数摘要**（flight-recorder.ts）：飞行记录器新增按 type 的会话级
累计计数，不随 ring 滚动淘汰、随 localStorage 跨重载、清空日志归零。
诊断表头扩展为 `flight N 条（起点 …）｜全程 upd=… synthed=… orphan=…
cs=… ce=… collapse=… drop=… bulk=… gate=… tree=…` —— 用户贴日志的**任何
一段**都能看到 ① 是否触发过（synthed）、守卫拦没拦（collapse）、有没有
程序化动树（tree）。

**组字取证盲区**（main.ts）：`in:bi` 补记 `comp=` 位 —— Android 宿主的
`beforeinput.isComposing` 是否可靠，是反推 ① 触发链的前提，此前只有
`in:i` 记了这一位。

**诊断快照**（diag/lines.ts）：`editor=` 截断 70→160 —— 70 字符只剩
第一个字，"编辑器到底有没有内容"无法判定。

判据：FLIGHT-08（ring 挤掉 50 条后全程计数仍为 450、跨重载从存储读回、
表头必带摘要、清空归零）+ DIAG-13（150 字符内容完整出现在 editor= 行），
均先红后改。单测 931/931、typecheck 干净。
